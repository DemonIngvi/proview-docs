# ADR-0001. Go для всех серверных сервисов

- **Статус:** принято
- **Дата:** 2026-11-06

## Контекст

Нужны сервисы с пиковой нагрузкой 20k RPS, низкой латентностью, малым потреблением памяти и быстрым стартом подов при автомасштабировании. Требование заказчика: сервисы на Go и JS.

## Решение

Все серверные сервисы пишутся на Go 1.26 со стандартной библиотекой как основой; сборка в статический бинарник без CGO.

## Обоснование

- Конкурентность (goroutines) и сетевой стек стандартной библиотеки дают десятки тысяч RPS на ядро без внешних фреймворков.
- Статический бинарник ~10–20 МБ, старт за миллисекунды — HPA добавляет поды быстро, образ distroless без ОС.
- Зрелые клиенты для всех выбранных систем: franz-go (Kafka), clickhouse-go (официальный), pgx (PostgreSQL).
- Предсказуемая латентность: GC с паузами < 1 мс, GOMEMLIMIT/GOMAXPROCS из лимитов контейнера.

## Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Rust | максимальная производительность, нет GC | долгая разработка, меньше специалистов, избыточно для I/O-bound нагрузки | запас производительности Go достаточен (замер: 3,5 мкс на обработчик) |
| Java/Kotlin (Spring/Quarkus) | богатая экосистема, Kafka Streams | память ×5–10, прогрев JIT, тяжёлые образы | хуже для быстрого масштабирования подов |
| Node.js | единый язык с SDK | однопоточный цикл, хуже на CPU-задачах (HMAC, JSON) при 20k RPS | нарушает требование «сервисы на Go» |

## Последствия

- ✅ Единый язык и инструменты (golangci-lint, go test, бенчмарки) во всех сервисах.
- ⚠️ Нет генериков-фреймворков уровня Spring — инфраструктурный код (platform) пишется самостоятельно.

## Когда пересмотреть

Если появятся CPU-bound задачи (ML-скоринг в аукционе), где выигрыш Rust/C++ окупит стоимость.
