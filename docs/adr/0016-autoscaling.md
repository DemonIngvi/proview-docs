# ADR-0016. Автомасштабирование: HPA по CPU, KEDA по лагу Kafka

- **Статус:** принято
- **Дата:** 2026-11-06

## Контекст

Нагрузка суточно меняется в 3 раза и имеет пики; stateless-сервисы масштабируются по CPU, а загрузчик — по объёму невыгруженных данных.

## Решение

HPA (autoscaling/v2) по CPU 60 % с быстрым ростом и медленным снижением для сервисов приёма и выдачи; для ingester — опциональный KEDA ScaledObject по лагу группы (в prod-профиле). PDB, topology spread по зонам и узлам, maxUnavailable 0 при выкладке.

## Обоснование

- CPU — точный индикатор нагрузки для CPU-bound обработчиков (JSON, HMAC).
- Лаг — прямой индикатор отставания загрузчика, CPU у него может быть низким при ожидании ClickHouse.
- Readiness collector падает при заполнении буфера — трафик перераспределяется ещё до масштабирования.

## Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Фиксированное число реплик | предсказуемо | переплата вне пика или отказ на пике | неэкономично |
| HPA по RPS (custom metrics) | точнее для выдачи | нужен prometheus-adapter | CPU достаточно; можно добавить |
| VPA | подбор ресурсов | конфликтует с HPA по CPU, перезапуски подов | использовать в режиме рекомендаций |

## Последствия

- ✅ Мощность следует за нагрузкой, отказ зоны переживается.
- ⚠️ KEDA — дополнительный оператор (опционально).

## Когда пересмотреть

После накопления реальных профилей нагрузки — пороги и минимальные реплики.
