# ADR-0009. Пул баннеров: PostgreSQL + неизменяемый снимок в памяти

- **Статус:** принято
- **Дата:** 2026-11-06

## Контекст

Выдача на 10k RPS с p99 < 20 мс, работа при недоступной БД; пул небольшой (сотни-тысячи баннеров), меняется редко; нужны транзакции и ограничения при редактировании.

## Решение

Источник истины — PostgreSQL (CloudNativePG); каждая реплика держит снимок пула в `atomic.Pointer`, перезагружая его раз в 10 с (± джиттер) и сразу после записи через API.

## Обоснование

- Горячий путь без сети и блокировок: выбор ~230 нс, 0 аллокаций.
- Stale-while-error: при отказе БД выдача продолжается последним снимком.
- PostgreSQL даёт CHECK-ограничения, транзакции, привычные миграции; CNPG — failover в Kubernetes.

## Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Запрос в PostgreSQL на каждый показ | всегда свежие данные | 10k запросов/с в БД, латентность и единая точка отказа | нарушает NFR2/NFR6 |
| Redis как основное хранилище | быстро, общий для реплик | сетевой вызов на каждый показ, ещё одна система, слабее ограничения данных | снимок в памяти быстрее и проще |
| Конфигурационный файл / ConfigMap | GitOps, просто | изменение = выкладка; нет API для трафик-менеджера | не подходит для оперативного управления |
| LISTEN/NOTIFY для мгновенного обновления | секундная свежесть | держит соединение на реплику, сложнее восстановление | 10 с достаточно; можно добавить позже |

## Последствия

- ✅ Выдача переживает недоступность БД; нагрузка на БД — 1 запрос в 10 с на реплику.
- ⚠️ Изменения пула видны с задержкой до ~12 с на других репликах.

## Когда пересмотреть

Если пул вырастет до сотен тысяч креативов с частыми изменениями — индексы в памяти и инкрементальные обновления (CDC).
