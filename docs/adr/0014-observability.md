# ADR-0014. Наблюдаемость: Prometheus-метрики и JSON-логи

- **Статус:** принято
- **Дата:** 2026-11-06

## Контекст

Нужно видеть RPS, латентность, обратное давление, лаг загрузки и свежесть пула; логи не должны сами стать нагрузкой при 20k RPS.

## Решение

Каждый сервис отдаёт `/metrics` (client_golang, OpenMetrics) на отдельном ops-порту, ServiceMonitor в чартах; логи — slog JSON в stdout без access-log на горячем пути, с ограничением частоты повторяющихся ошибок.

## Обоснование

- Метрики дешевле логов на каждый запрос и дают SLO/алерты.
- Ops-порт отделён от публичного — метрики не доступны снаружи.
- JSON-логи собираются любым агентом (Vector, Fluent Bit, Promtail).

## Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Access-log на каждый запрос | полный след | ~20k строк/с только от выдачи, стоимость хранения | метрики + сэмплирование ошибок достаточно |
| OpenTelemetry (трейсы + метрики) | сквозная трассировка | SDK и коллектор, накладные расходы, хранилище трейсов | запланировано в развитии для пути collector → ingester |
| StatsD / push-метрики | проще для коротких задач | не стандарт Kubernetes-мониторинга | Prometheus — де-факто стандарт |

- ⚠️ Нет сквозной трассировки отдельного события (есть event_id в raw).
