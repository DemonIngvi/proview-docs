# ADR-0019. Репозиторий на сервис, GitHub Actions, GHCR

- **Статус:** принято
- **Дата:** 2026-11-06

## Контекст

Требование: отдельный репозиторий на каждый сервис и на документацию, удобная доставка в инфраструктуру.

## Решение

Шесть репозиториев кода (`proview-*`) и `proview-docs`; в каждом CI: lint → unit → интеграционные тесты на реальных зависимостях (services) → helm lint + kubeconform → multi-arch образ в GHCR (+SBOM, provenance, Trivy) → по тегу публикация чарта. `proview-deploy` ночью собирает все main-ветки и гоняет e2e, chaos и короткую нагрузку. Общий код (`internal/platform`, ~200 строк) копируется, а не выносится в библиотеку.

## Обоснование

- Независимые релизы и права на уровне сервиса.
- Межсервисные контракты проверяются дважды: контрольными векторами в unit-тестах и e2e в deploy.
- Копия маленького инфраструктурного пакета дешевле, чем версионирование общей библиотеки по шести репозиториям.

## Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Монорепозиторий | атомарные изменения контрактов, один CI | противоречит требованию; сложнее разграничение прав | требование заказчика |
| Общая Go-библиотека proview-kit | нет дублирования | каскад обновлений по репозиториям, связанное версионирование | дублирование 200 строк дешевле |
| GitLab CI / Jenkins | самостоятельный хостинг | код уже на GitHub | Actions — нативно для GitHub |

## Последствия

- ✅ Каждый сервис доставляется независимо; совместимость проверяется ночным e2e.
- ⚠️ Изменение контракта требует согласованных PR в 2–3 репозиториях.

## Когда пересмотреть

Если изменения контрактов станут частыми — монорепозиторий или общий модуль контрактов.
