# ADR-0005. ClickHouse как аналитическое хранилище

- **Статус:** принято
- **Дата:** 2026-11-06

## Контекст

Десятки миллиардов событий в месяц, агрегации по времени и измерениям с ответом < 1 с, дешёвое хранение, open source, развёртывание в Kubernetes.

## Решение

Сырые события и агрегаты хранятся в ClickHouse 25.8 LTS (1 шард × 3 реплики, Replicated-БД, Keeper).

## Обоснование

- Колоночное хранение и сжатие ×10–20: ~35 байт на событие, агрегаты по месяцам — сотни миллисекунд.
- Вставка сотен тысяч строк/с на узел; материализованные представления строят агрегаты при вставке.
- AggregatingMergeTree + uniqState — уникальные посетители, суммируемые по любым срезам.
- Дедупликация вставок по токену — основа идемпотентной загрузки; оператор Altinity для Kubernetes.

## Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Apache Druid / Pinot | real-time OLAP, встроенный приём из Kafka | много компонентов (broker, historical, coordinator…), сложная эксплуатация | ClickHouse проще при той же задаче |
| PostgreSQL + TimescaleDB | SQL, знаком команде | на 50k строк/с и миллиардах строк — дорого по CPU и диску | не тянет объём без шардирования |
| Elasticsearch/OpenSearch | поиск, Kibana | дорогое хранение, слабые агрегаты по большим объёмам | не для числовой аналитики |
| BigQuery / Snowflake | без эксплуатации | SaaS, стоимость за запросы, данные у третьей стороны | ограничение: только open source |

## Последствия

- ✅ Запросы админки по 90 дням < 1 с из агрегатов.
- ⚠️ Не OLTP: обновления/удаления дорогие; нужно проектировать ORDER BY под запросы.

## Когда пересмотреть

При записи выше возможностей одного шарда — переход на Distributed-таблицы.
