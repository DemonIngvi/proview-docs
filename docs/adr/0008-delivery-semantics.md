# ADR-0008. Семантика доставки: at-least-once + идемпотентная вставка

- **Статус:** принято
- **Дата:** 2026-11-06

## Контекст

Деньги считаются по показам и кликам: дубли и потери недопустимы. При этом коллектор должен отвечать за миллисекунды.

## Решение

Продюсер: acks=all + idempotence, ответ клиенту после постановки в буфер. Загрузчик: at-least-once с коммитом после вставки и детерминированным токеном дедупликации пачки. SDK: повтор с тем же seq (стабильный event_id).

## Обоснование

- Повтор пачки после сбоя вставки или краха загрузчика отбрасывается ClickHouse (проверено тестами).
- Ответ 202 до подтверждения Kafka держит p99 приёма в единицах миллисекунд.
- event_id = impression_id:seq позволяет дедуплицировать повторы SDK в сырых данных при разборе.

## Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Exactly-once транзакции Kafka + Connect EOS | строгая гарантия | сложность, транзакционный продюсер медленнее, всё равно нужна идемпотентность на стороне ClickHouse | идемпотентная вставка даёт тот же результат проще |
| Синхронный ответ после ack Kafka | нет окна потери на крахе пода | латентность приёма = латентность Kafka (единицы-десятки мс), больше открытых соединений | окно потери ~10 мс трафика пода приемлемо |
| ReplacingMergeTree по event_id | дедуп повторов SDK | дедуп только при слиянии, FINAL дорогой, агрегаты через MV всё равно получат дубли | не решает задачу для агрегатов |
| At-most-once | просто | потери при любом сбое | неприемлемо |

## Последствия

- ✅ Сбой ClickHouse или загрузчика не теряет и не удваивает события.
- ⚠️ Крах пода collector теряет буфер, не подтверждённый Kafka (≤ linger 10 мс + in-flight); повтор SDK после сетевой ошибки может дать дубль события (редкий, видим в raw по event_id).

## Когда пересмотреть

Если бизнес потребует нулевого окна потерь на крахе пода — режим синхронного ack для кликов.
