# ADR-0007. База-агрегатор: MV в AggregatingMergeTree внутри ClickHouse

- **Статус:** принято
- **Дата:** 2026-11-06

## Контекст

Требование: события «грузятся в базу-агрегатор», из которой админка строит срезы. Агрегаты должны быть свежими (секунды), дешёвыми и согласованными с сырыми данными.

## Решение

Отдельная база `proview_agg` с таблицами `banner_stats_1m` (TTL 14 дней) и `banner_stats_1h` (730 дней), которые заполняют материализованные представления при каждой вставке в `proview.events_raw`.

## Обоснование

- Свежесть = момент вставки, без пакетных заданий и расписаний.
- Агрегаты согласованы с сырыми данными по построению; дедупликация вставки распространяется на MV.
- Минутная гранулярность для оперативного мониторинга, часовая — для истории; запросы выбирают таблицу по диапазону.
- Отдельная база даёт отдельные права: аналитика читает только `proview_agg`.

## Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Отдельная БД-агрегатор (PostgreSQL) + пакетная джоба | знакомый SQL, отдельный контур | задержка до окончания джобы, ещё одна система, риск расхождения с raw | хуже свежесть и сложнее |
| Агрегация в потоке (Kafka Streams / Flink) | гибкие окна, поздние события | отдельный кластер обработки, сложность состояния | избыточно для суммирующих метрик |
| Только сырые данные + projections | меньше объектов | запросы по 90 дням сканируют миллиарды строк | нарушает NFR8 |
| SummingMergeTree | проще | не поддерживает uniq-состояния (уникальные посетители) | нужен AggregatingMergeTree |

## Последствия

- ✅ Срезы по 90 дням читают тысячи, а не миллиарды строк.
- ⚠️ Новое измерение в срезе требует миграции агрегатов (и пересчёта из raw за 30 дней).

## Когда пересмотреть

Если понадобятся окна по сессиям или поздние события старше суток — потоковая агрегация.
