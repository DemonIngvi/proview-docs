# ADR-0006. Собственный Go-загрузчик Kafka → ClickHouse

- **Статус:** принято
- **Дата:** 2026-11-06

## Контекст

Нужно доставить события из Kafka в ClickHouse крупными пачками, ровно один раз в агрегатах, с DLQ для битых сообщений, с метриками и управляемым масштабированием.

## Решение

Отдельный сервис event-ingester на Go: пачка по размеру/времени → вставка с `insert_deduplication_token` → коммит смещений.

## Обоснование

- Полный контроль семантики: коммит только после успешной вставки, детерминированный токен пачки.
- DLQ с причиной ошибки, метрики пачек и задержек, бесконечные повторы с backoff.
- Масштабирование числом подов (≤ партиций), KEDA по лагу; не нагружает ClickHouse фоновыми потоками.
- Миграции схемы живут рядом с кодом, который пишет данные.

## Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Kafka table engine ClickHouse + MV | без отдельного сервиса | парсинг и ошибки внутри ClickHouse, сложнее DLQ и наблюдаемость, нагрузка на сервер БД, at-least-once с дублями при сбоях | меньше контроля и хуже отладка |
| Kafka Connect + ClickHouse Sink | готовый коннектор, exactly-once режим | JVM-кластер Connect для одного потока, отдельная эксплуатация | избыточная инфраструктура |
| Vector / Fluent Bit | лёгкие агенты | нет коммита после вставки с дедупликацией по пачкам | слабее гарантии |
| ClickPipes (ClickHouse Cloud) | управляемый | SaaS | ограничение: open source, своя инфраструктура |

## Последствия

- ✅ Доставка ровно один раз подтверждена chaos-тестом (простой ClickHouse, SIGKILL).
- ⚠️ Ещё один сервис в сопровождении (~400 строк кода).

## Когда пересмотреть

Если ClickHouse Kafka engine получит управляемую семантику коммитов и DLQ на уровне, сравнимом с текущей.
