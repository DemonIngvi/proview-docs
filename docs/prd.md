# ProView — Product Requirements Document (PRD)

> BMAD Method · артефакт PM · версия 1.0 · 2026-11-06 · основа: [brief.md](brief.md)

## 1. Цели и контекст

ProView выдаёт рекламные баннеры по преднастройкам рекламных мест, измеряет вовлечённость (видимость, наведение, клик, время активности) и показывает её в админке с настраиваемыми срезами. Целевая нагрузка — 20 000 запросов/с на публичных API. Система масштабируется горизонтально и не теряет принятые события при отказе любого одного компонента хранения или обработки.

## 2. Требования

### Функциональные (FR)

| ID | Требование |
|---|---|
| FR1 | Страница запрашивает баннер для рекламного места (placement) и получает креатив, ссылку перехода, размеры, `impression_id` и подписанный токен показа |
| FR2 | Место (преднастройка) задаёт идентификатор и размер. Баннер привязывается к одному или нескольким местам |
| FR3 | Баннер имеет вес. Выбор среди подходящих — взвешенный случайный |
| FR4 | Таргетинг баннера: список стран, классов устройств (desktop / mobile / tablet), период показа `starts_at`…`ends_at`. Пустой список — без ограничений |
| FR5 | Если подходящего баннера нет, ответ «нет заполнения» (204), место скрывается |
| FR6 | API управления пулом: создание, изменение и деактивация баннеров, создание мест. Доступ по токену, только во внутренней сети |
| FR7 | SDK фиксирует события `impression`, `viewable` (≥ 50 % площади ≥ 1 с, IAB), `hover` с длительностью, `click`, `active_time` (видим и вкладка активна) |
| FR8 | SDK доставляет события при уходе со страницы и повторяет отправку при перегрузке или сетевой ошибке |
| FR9 | Сборщик принимает пакеты событий, проверяет токен показа и отклоняет поддельные, просроченные и некорректные события. Боты не учитываются |
| FR10 | Событие обогащается страной, классом устройства, хостом страницы и временем приёма |
| FR11 | События попадают в ClickHouse. Агрегаты (минута, час) строятся автоматически |
| FR12 | Невалидные сообщения откладываются в отдельную очередь (DLQ) для разбора |
| FR13 | Админка показывает KPI периода с изменением к предыдущему, динамику метрики (опционально в разрезе), воронку, тепловую карту день × час, срез по измерению с таблицей |
| FR14 | Параметры среза: период, шаг, метрика, разрез, фильтры по баннеру, месту, стране и устройству, часовой пояс, автообновление. Срез воспроизводится по ссылке |
| FR15 | Метрики: показы, видимые показы, клики, CTR, видимость, доля наведений, среднее время наведения, среднее активное время, уникальные посетители |
| FR16 | Доступ к админке по паролю или через SSO-прокси |

### Нефункциональные (NFR)

| ID | Требование | Как проверяется |
|---|---|---|
| NFR1 | 20 000 RPS суммарно на `GET /v1/banner` + `POST /v1/events`, ошибки < 0,1 % | k6 `load/k6-pageviews.js`, расчёт ёмкости в [architecture.md §7](architecture.md#7-ёмкость-и-масштабирование) |
| NFR2 | p99 серверной обработки `GET /v1/banner` < 20 мс, `POST /v1/events` < 20 мс | метрики `*_http_request_duration_seconds`, бенчмарки |
| NFR3 | Горизонтальное масштабирование каждого сервиса без координации (stateless) | HPA, KEDA |
| NFR4 | Принятое событие (202) не теряется при отказе ClickHouse, загрузчика или одного брокера Kafka | `scripts/chaos.sh`, RF 3 / min ISR 2 |
| NFR5 | Повторная доставка не создаёт дублей в агрегатах при повторе пачки | интеграционный тест ingester |
| NFR6 | Выдача баннеров работает при недоступном Postgres (последний снимок) | unit-тест pool |
| NFR7 | Задержка событие → агрегат p95 < 10 с | e2e (замер ~2 с) |
| NFR8 | Ответ API аналитики p95 < 1 с (90 дней) | агрегаты 1h, кэш, `max_execution_time` |
| NFR9 | Безопасность: контейнеры без root, read-only FS, секреты вне образов, параметризованный SQL, CSP, минимальные права в ClickHouse | Helm-шаблоны, golangci-lint (gosec), Trivy в CI |
| NFR10 | Наблюдаемость: метрики Prometheus, JSON-логи, health и readiness | `/metrics`, `/healthz`, `/readyz` |
| NFR11 | Поставка: образ на каждый коммит в main, версионированные образы и Helm-чарты по тегу, один umbrella-чарт для всей системы | GitHub Actions, GHCR |
| NFR12 | Приватность: IP не хранится, посетитель — псевдонимный id первой стороны | код collector и SDK |

## 3. Цели UI

Админка — одна страница-дашборд для потребителя среза (менеджера рекламы). Фильтры в одну строку над графиками. KPI сверху, затем динамика, воронка и тепловая карта, детальный срез с таблицей. Светлая и тёмная темы, адаптивность до 390 px, табличная альтернатива каждому графику. Подробно — [front-end-spec.md](front-end-spec.md).

## 4. Технические допущения

Микросервисы в отдельных репозиториях: Go 1.26, Kafka (KRaft), ClickHouse, PostgreSQL. Kubernetes и Helm, инфраструктура через операторы. Обоснование каждого решения и альтернативы — [adr/](adr/README.md).
