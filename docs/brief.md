# Project Brief: ProView

> BMAD Method · артефакт аналитика (Analyst) · версия 1.0 · 2026-11-06

## Резюме

ProView — платформа показа рекламных баннеров с измерением вовлечённости. Страница площадки запрашивает баннер для своего рекламного места. Браузерный SDK фиксирует показ, фактическую видимость, наведение курсора с длительностью, клик и активное время. События через Kafka попадают в ClickHouse, откуда админка строит настраиваемые срезы с визуализацией.

## Проблема

1. Счётчик «показов» без видимости и времени не отвечает на вопрос, видел ли человек рекламу. Решения о бюджете принимаются по завышенным цифрам.
2. Готовые счётчики (пиксели, сторонние SaaS) не дают сырых событий и собственных срезов. Данные уходят третьей стороне.
3. Рекламный трафик пиковый: до **20 тыс. запросов/с**. Потеря статистики при сбое хранилища — прямые финансовые потери (оплата за показы и клики).

## Решение

| Часть | Что делает |
|---|---|
| Выдача баннера | выбирает креатив по преднастройке места, таргетингу (страна, устройство, период) и весу; выдаёт подписанный токен показа |
| SDK | измеряет показ, видимость по стандарту IAB, наведение, клик и активное время. Не теряет события при уходе со страницы |
| Сбор событий | проверяет токен, отсекает ботов и подделки, отвечает сразу, буферизует в Kafka |
| Загрузка | пачками пишет в ClickHouse без дублей при повторах. Агрегаты поминутно и почасово |
| Аналитика | KPI, динамика, воронка, тепловая карта, срезы по баннеру, месту, стране и устройству |

## Пользователи

| Роль | Задача |
|---|---|
| Менеджер рекламы (потребитель среза) | сравнить креативы и места по CTR, видимости и времени внимания, выгрузить срез ссылкой |
| Трафик-менеджер | завести баннер, задать вес, таргетинг и период показа |
| Владелец площадки | вставить два тега на страницу и не замедлить её |
| Инженер эксплуатации | развернуть в Kubernetes, масштабировать, пережить сбой без потери данных |

## Цели и метрики успеха

| Цель | Метрика | Порог |
|---|---|---|
| Выдержать пик | RPS на публичных API | 20 000, ошибки < 0,1 % |
| Быстрая выдача | p99 `GET /v1/banner` на сервере | < 20 мс |
| Не терять события | доля событий, принятых (202) и не попавших в ClickHouse | 0 при отказе ClickHouse или загрузчика |
| Свежесть данных | задержка от события до агрегата | p95 < 10 с |
| Отзывчивая админка | ответ API срезов | p95 < 1 с на 90 днях данных |

## Объём MVP

**Входит:** всё из таблицы «Решение», управление пулом через API, Docker и Helm, CI, автотесты (unit, интеграционные, e2e, chaos, нагрузка), документация.

**Не входит в MVP:** аукцион и биддинг (RTB), частотное ограничение показов на посетителя, атрибуция конверсий, UI управления пулом (сейчас только API), A/B-тесты креативов, GeoIP внутри платформы (страна берётся из заголовка CDN или ingress).

## Ограничения и допущения

- Только open source компоненты, без облачных SaaS. Развёртывание в любом Kubernetes ≥ 1.29.
- Сервисы на Go, клиентская часть на JS.
- Страна посетителя приходит заголовком от CDN или ingress (`CF-IPCountry`, GeoIP-модуль ingress).
- IP-адреса не хранятся. Посетитель — случайный первичный идентификатор в `localStorage`.

## Риски

| Риск | Мера |
|---|---|
| Накрутка кликов и показов | HMAC-токен показа, фильтр ботов, rate-limit на ingress. Дальнейшее развитие — антифрод по сырым событиям |
| Перегрузка ClickHouse запросами админки | только агрегаты, кэш с singleflight, лимиты времени и памяти, пользователь только для чтения |
| Блокировщики рекламы режут SDK | собственный домен для API, без сторонних доменов. Принимается как ограничение рынка |
| Дубли при повторах | детерминированные `event_id` и токены дедупликации пачек |
